# 14 — WebAssembly 2.0 / 3.0: анализ, классы ёмкости, единый код

> **Статус: принято и реализовано 2026-07-20.** Источник анализа —
> спецификация W3C **WebAssembly Release 3.0 (2026-07-10)** (PDF, §7.8.2
> «Change History → Release 3.0», прочитан лично) и **живые пробы** на этой
> машине: wasmtime 41.0.3, wasmer 7.2.0, rustc stable 1.96 / nightly 1.98.
> Спека отвечает на три вопроса: что из Wasm 3.0 нужно plugmem, как один
> код и один формат обслуживают оба поколения, и что показали рантаймы.

## 0. Суть решения (TL;DR)

**«Версия wasm» для plugmem — это класс адресного пространства сборки, а
не ветка кода, не feature-флаг и не поле формата.** Один и тот же
исходник ядра собирается под все таргеты; один и тот же файл базы
читается всеми сборками, чьё адресное пространство вмещает его лимиты.

| Класс | Таргет | Адресация | Потолок памяти | Статус |
|---|---|---|---|---|
| **v2-класс** (Wasm 2.0) | `wasm32v1-none` / `wasm32-unknown-unknown` | 32-бит | 4 ГиБ (наш бюджет ≤ 2 ГиБ) | default, работает везде |
| **v3-класс** (Wasm 3.0, memory64) | `wasm64-unknown-unknown` | 64-бит | 2⁶⁴ (браузеры сегодня ~16 ГиБ) | opt-in; Tier 3, nightly + build-std |
| native | x86-64 / aarch64 | 64-бит | ОЗУ хоста | как было |

- Никакого «выбора версии» в API глаголов не нужно: возможности выбираются
  **конфигом** (`max_bytes` и прочие лимиты), а не переключателем. База с
  лимитами ≤ 2 ГиБ открывается везде; база с `max_bytes` > потолка 32-бит
  хоста — только на 64-битных сборках.
- **Миграция 2.0 → 3.0 = открыть тот же файл.** Формат байт-в-байт общий
  (доказательство — §3). Обратной миграции «большой базы в маленький хост»
  не существует физически; ядро отвечает на такую попытку типизированно:
  `ConfigMismatch("database requires a 64-bit address space")` — файл не
  «битый», хосту не хватает адресного пространства (реализовано в
  `Config::decode`, тест исполняет обе ветви: 64-битную на нативе,
  32-битную — на `wasm32-wasip1` под wasmtime).

## 1. Разбор Wasm 3.0 по спецификации: что берём и почему

Полный список Release 3.0 (§7.8.2 PDF) и вердикт для plugmem:

| Фича 3.0 | Вердикт | Обоснование |
|---|---|---|
| **64-bit address space (memory64)** | **берём** — это и есть v3-класс | снимает потолок 4 ГиБ линейной памяти; паспорт ёмкости масштабируется с ~1M фактов до десятков миллионов без изменений кода. Ядро собралось под `wasm64-unknown-unknown` **без единой правки** — плата за дисциплину «все кодеки фиксированной ширины» |
| **Relaxed SIMD** | **не берём в детерминированных путях** (см. ниже) | инструкции объявлены недетерминированными и implementation-dependent. Сборка HNSW-графа зависит от результатов dot-продуктов → любой недетерминизм ломает контракт «реплей журнала = байт-в-байт снапшот». Отдельно: `i16x8.relaxed_dot_i8x16_i7x16_s` выглядит созданным для нас, но требует 7-битный (беззнаковый) второй операнд — наша симметричная i8-квантизация даёт [-127, 127]; переход на асимметричную схему ради него — пересмотр формата слота, не окупается |
| simd128 (из 2.0) | **совместимо, проверено** | целочисленный SIMD детерминирован; сборка с `-Ctarget-feature=+simd128` даёт **идентичный хеш снапшота** (§3). Автовекторизация hamming/dot уже рассчитана на него (specs/04) |
| **Multiple memories** | не нужно | Rust/LLVM не эмитит вторые памяти; наш zero-copy обмен снапшотами живёт в одной линейной памяти, секции и так плоские |
| **GC (managed types)** | не нужно | адресовано языкам с управляемой кучей (Java/Kotlin/Dart). Rust компилируется в линейную память; вся наша модель — плоские арены именно затем, чтобы кучи объектов не существовало |
| **Typed function references** | не нужно | оптимизация call_indirect для языков с витринами функций; наш код мономорфен, динамических вызовов нет |
| **Exception handling** | не нужно | в ядре нет паник by design (panic = баг, ошибки типизированы `Result`); Rust panic=abort в наших wasm-сборках. try/throw/catch адресованы C++/Java-стилю |
| **Tail calls** | не нужно | Rust их не эмитит; наши алгоритмы итеративные (beam search — цикл, не рекурсия) |
| Extended const expressions | нейтрально | инструментальное удобство линкеров; нас не касается |
| **Deterministic profile** | **союзник, соблюдаем уже сейчас** | подмножество 3.0 со строго определённым поведением. Ядро в него укладывается сознательно: целочисленные расстояния, `total_cmp`-порядки, libm-софтматематика, никакого relaxed SIMD в путях состояния. Это буквально наш контракт реплея, теперь названный стандартом |
| Custom annotations (текстовый формат) | нейтрально | метаданные .wat, семантики не несут |

Вывод: **из всего Release 3.0 движку нужен ровно memory64**; simd128
полезен и совместим; всё остальное адресовано другим классам языков или
инструментам. «Поддержка Wasm 3.0» для plugmem — это ёмкость, не набор
инструкций.

## 2. Почему формат один и версия в заголовок не пишется

Проверено по всем кодекам (2026-07-20):

- **Config-блок**: все `usize`-поля пишутся фиксированными `u64 LE`
  (`ENCODED_LEN` = 188 не зависит от платформы); декод — checked
  `usize::try_from` с типизированным отказом (§0).
- **Заголовки арен/структур**: только `u32`/`u64` фиксированной ширины
  (`plugmem-arena`: shards/pages `u32`, total `u64`; BlobHeap/Interner/
  ChunkPool — `u32`-счётчики).
- **Контейнер снапшота**: оффсеты/длины секций `u64`, все границы
  считаются в `u64`-арифметике **до** любого `as usize`.
- **Журнал**: длины `u32`, значения LEB128/фиксированные — ширина
  платформы не участвует.

Единственное, что реально отличает «64-битную базу» — влезают ли её
сохранённые лимиты в `usize` хоста, и это **полностью выводимо из
config-блока** (`max_bytes` и соседние поля). Отдельное поле «wasm-версия»
в заголовке было бы производным состоянием: его пришлось бы валидировать
на согласованность с конфигом, а расходиться им нельзя по построению.
По принципу каноничности формата (specs/03: dump→load→dump байт-в-байт,
никаких избыточных полей) — **поле не вводим; меткой класса служит сам
`max_bytes`**. Резервные байты заголовка не тронуты; решение обратимо
до заморозки формата, если появится настоящий (не производный) сигнал.

## 3. Живые пробы (методика и результаты, 2026-07-20)

Пробник: no_std-сценарий поверх публичного API (200 фактов с векторами
dim 64, entity/tags/links, forget каждый 7-й, revise каждый 11-й,
`maintain` с физическим purge, `recall`, `snapshot_bytes`) → `xxh3(байты
снапшота)`. Один исходник, четыре сборки:

| Сборка | Рантайм | Результат |
|---|---|---|
| native x86-64 (stable) | — | `0x87dd19325f92da30` — эталон |
| `wasm32-unknown-unknown` | wasmtime 41.0.3 | **тот же хеш** |
| `wasm32-unknown-unknown` + `+simd128,+relaxed-simd` | wasmtime (`-W relaxed-simd`) | **тот же хеш** (relaxed-инструкции компилятор сам не эмитит — недетерминизм не проникает без явных intrinsics) |
| `wasm64-unknown-unknown` (nightly, `-Zbuild-std=core,alloc`) | wasmtime 41.0.3 | **тот же хеш**; memory64 включён в wasmtime по умолчанию |
| `wasm64-unknown-unknown` | wasmer 7.2.0 | ❌ **не запускается**: `Validate("memory64 must be enabled for 64-bit tables")`, а с `--enable-memory64` все три бэкенда (cranelift/llvm/singlepass) отвечают «does not support the required features» — wasm64-модуль из Rust несёт 64-битную таблицу, которую wasmer пока не умеет |
| `wasm32-unknown-unknown` | wasmer 7.2.0 | **тот же хеш** |

**Снапшот доказанно идентичен байт-в-байт на 32-битной, 64-битной wasm и
нативной сборках.** Это главный инженерный итог: файл переносим между
поколениями без миграторов.

Состояние рантаймов (актуально на 2026-07-20): **wasmtime — полная
поддержка v3-класса из коробки; wasmer — только v2-класс.** Браузеры
(Chrome/Firefox) заявляют Wasm 3.0 с сентября 2025. Дефолт продукта
остаётся v2-классом ровно поэтому: он исполняется всюду.

Дополнительно: **весь контрактный тест-сьют ядра прогнан на настоящем
32-битном таргете** `wasm32-wasip1` под wasmtime (proptest-секции
погейчены `cfg(not(target_family = "wasm"))` — их харнесс нативный;
детерминированные контрактные тесты — общие). Результат — в §5.

## 4. Как это доедет до обёрток (этап 5, зафиксировано заранее)

- **CLI / MCP** — нативные 64-битные бинарники: оба класса ёмкости
  понимают **автоматически** (native = 64-бит адресация). Никакого
  «указания версии в запросе» для файлов не требуется — бинарник просто
  открывает любой файл; выбор класса делается при **создании** базы
  (`max_bytes` в конфиге).
- **npm-пакет** — два артефакта из одного кода: `wasm32` (default,
  везде) и `wasm64` (opt-in, для баз > 2 ГиБ; требует движка с
  memory64 — браузеры и wasmtime уже, Node — по флагу V8). JS-обвязка
  выбирает артефакт по опции `open({ memory64: true })`; формат общий,
  «миграция» между артефактами — открытие того же файла.
- Один Rust-код, никакой шаблонизации по версиям не понадобилось: всё,
  что зависит от разрядности, уже выражено через `usize` + checked-декод.

## 5. Реализовано в этом заходе

1. `Config::decode`: переполнение `usize` 32-битного хоста →
   `ConfigMismatch("database requires a 64-bit address space")` (было
   некорректное `Corrupt`); rustdoc объясняет семантику. Тест
   `a_64bit_class_database_is_refused_on_32bit_hosts_with_a_typed_error`
   исполняет обе ветви (64-бит: лимит принят; 32-бит: типизированный
   отказ) — вторая ветвь реально исполнена на `wasm32-wasip1`.
2. proptest-секции 7 интеграционных тестов + пример `measure_remember`
   погейчены от wasm-таргетов — контрактный сьют ядра стал
   кросс-таргетным. Прогон: `CARGO_TARGET_WASM32_WASIP1_RUNNER="wasmtime
   run --dir=." cargo test -p plugmem-core --target wasm32-wasip1`.
3. Пробы §3 (эквивалентность снапшота на четырёх сборках, wasmtime/wasmer).
4. README core/host: кросс-ссылки и заметка о классах ёмкости.

Гейты воспроизведения:

```sh
# v2-класс (как раньше, обязательный):
cargo build -p plugmem-arena -p plugmem-core --target wasm32v1-none --no-default-features
# 32-битный прогон сьюта (wasmtime):
CARGO_TARGET_WASM32_WASIP1_RUNNER="wasmtime run --dir=." \
  cargo test -p plugmem-core --target wasm32-wasip1
# v3-класс (nightly-гейт, Tier 3):
cargo +nightly build -p plugmem-core --target wasm64-unknown-unknown \
  -Zbuild-std=core,alloc --no-default-features
```

## 6. Открытые вопросы

- `wasm64-unknown-unknown` — Tier 3: следим за тиром; когда цель станет
  Tier 2 с прекомпилированной std, nightly-гейт станет stable-гейтом.
- wasmer: пере-проверить 64-битные таблицы в следующих мажорах.
- Явный simd128-бенч (native vs wasmtime, hamming/dot) — в бенч-стенд
  этапа 5 (specs/07 §4 это уже предусматривает).
- npm-артефакт wasm64 и опция `open({ memory64 })` — этап 5 (specs/06).
