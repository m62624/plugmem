# 04 — индексы и hybrid recall

> Одно хранилище фактов — несколько входов в него: лексический (BM25),
> семантический (векторы), структурный (теги, сущности, граф), временной.
> Recall сливает их в один ранжированный результат и собирает компактный
> контекст под токен-бюджет.

## 1. Токенизатор (в ядре: нужен и в wasm) — **v2, реализовано 2026-07-18**

Первая версия (наивные alphanumeric-раны) заменена по решению пользователя на
стек, к которому сходятся топовые лексические движки (Lucene ICU/Standard,
SQLite FTS5 `unicode61`), собранный из чистых `core`-крейтов unicode-rs
(версии и wasm-проба — `specs/08`; +163 КиБ таблиц в wasm-бинаре — принято):

1. **NFKC-нормализация** входа (fullwidth → ASCII, лигатуры ﬁ → fi,
   декомпозированные марки собираются). ASCII-текст идёт мимо (identity,
   fast path ~35%).
2. **Сегментация UAX #29** (`unicode-segmentation`) — стандарт ICU.
   Следствия: `don't`/`o'clock` целые (апостроф соединяет буквы), `3.14`,
   `v1.2.3`, `1,000`, `docs.rs` целые (`.`/`,` соединяют цифры/буквы),
   `snake_case` целый (`_` соединяет), `gpt-4o` делится по дефису.
3. **Фолдинг токена**: полный Unicode lowercase; латинская диакритика
   срезается до ASCII-базы (`café` → `cafe`, класс FTS5 `remove_diacritics`),
   **только** для латиницы — кириллическое `й` не трогаем (классическая
   ошибка unicode61); русское `ё` → `е` (конвенция всех крупных русских
   поисков). Токены каноничны: неподвижная точка токенизации
   (property-тест).
4. **CJK**: хань и хирагана выходят из UAX #29 посимвольно → соседние
   склеиваются в перекрывающиеся **биграммы** (схема Lucene
   `CJKBigramFilter`, стандарт без словарей); одиночный символ — юниграмма.
   Катакана и хангыль сегментируются в слова и остаются словами.
- Без стемминга/лемматизации в v1. Токен → `TermId` через Interner; длиннее
  64 Б — обрезка по границе символа.
- Замеры (native, criterion): ASCII ~17 нс/Б, смешанный ру/en ~29 нс/Б,
  CJK ~19 нс/Б → худший случай `max_text` 4 КиБ ≈ 70–120 мкс — в бюджете
  remember; типичные 150 Б ≈ 3–5 мкс.
- API: `Tokenizer` со скретч-буферами (переиспользуются — ноль аллокаций
  после прогрева, инвариант recall).

## 2. Лексический индекс (BM25)

Структуры:

- `postings: Arena<PostingHandle>` (Uniform, ключ TermId, слот 20 Б:
  term 4 + ListHandle 12 + df u32) — терм → список документов.
- Постинги в `ChunkPool`: последовательность записей
  `[delta(fact_id) varint][tf u8]`, fact_id возрастают (вставки фактов
  монотонны по id ⇒ append в хвост, сортировка бесплатна).
- `doc_len: Arena<DocLen>` (Uniform, слот 8 Б: fact 4 + len u16 + pad) +
  глобальные `total_docs`, `total_len` в статистике движка.

Скоринг: классический BM25, k1 = 1.2, b = 0.75 (константы в Config).
Запрос: термы запроса → для каждого декод постингов с аккумуляцией
`score[fact] += idf·tf_norm` в переиспользуемом open-addressing скретче →
top-K сортировкой малого буфера. Стоимость O(Σ df) — на нашем масштабе без
WAND-эвристик (отмечено как v2-оптимизация при df-миллионах).

**Стоп-частотный фильтр (реализовано, замерено 2026-07-18):** терм запроса
с df > корпус/8 (и df > 1024) выбрасывается из запроса — при idf-взвешивании
он почти не различает документы, а его постинг-лист доминирует в стоимости
(запрос со словом класса «the» стоил O(корпус): 2.5 мс на 100k). Если
стоп-частотны *все* термы — остаётся наименее частый (запрос всегда
отвечает). После фильтра структурный recall @100k = **61 мкс** (бюджет
200 мкс); правило детерминировано и покрыто тестом бенча.

Tombstone/closed факты фильтруются на кандидате (бит-чек по записи), из
постингов физически выпадают при `maintain`-пересборке.

## 3. Теги и сущности

- tag → facts: `Arena<TagHandle>` (ключ TermId) + ChunkPool-списки
  varint-дельт fact_id (сортированы по построению).
- Фильтр тегов в запросе: пересечение отсортированных списков (merge),
  результат — allow-набор для остальных источников (битовая карта в скретче).
- entity → facts: та же схема (`EntityHandle`), заполняется при remember.

## 4. Временной индекс

Арена из `02` (ключ `[recorded_at BE | fact_id]`). Запросные режимы:

- `range(a, b)` — факты, записанные в окне (эпизодическая память: «что было в
  марте») → range-скан;
- `as_of(t)` — фильтр валидности на кандидатах любого источника (O(1) на
  кандидата по записи факта);
- recency-буст в ранжировании (см. слияние).

## 5. Векторный слой

> **Статус: фаза 1 (Flat) реализована 2026-07-19.** `plugmem-core::index::vecpool`:
> плоский `VecPool` (не арена, не BlobHeap — flat-скану нужна идеальная
> локальность), слот `[fact u32 | scale f32 | sig u64×words | q i8×dim]`,
> симметричная i8-квантизация L2-нормированного вектора, двухфазный поиск
> (хэмминг по сигнатурам → точный квант-косинус на `max(4k, 64)` кандидатах).
> Подключён как четвёртый источник recall (бит `VEC`, вес `w_vec`) и как
> сигнал similar-детекции (`SimilarReason::VectorCosine`, порог
> `similar_cos`). Сырой f32 едет в журнале — реплей переквантует той же
> чистой функцией и воспроизводит слот байт-в-байт (property-тест). Секция
> снапшота `VEC_POOL`, загрузчик проверяет биекцию факт↔слот, конечность
> scale и совпадение сигнатуры со знаками (panic-free на любых байтах).
> Counters-гейт: точных dot'ов ровно `min(кандидаты, живые)`. Юнит-тест
> квантования: |квант-косинус − f32-косинус| < 0.05; recall@10 flat против
> brute-force ≥ 0.8. HNSW (фаза 2) — этап 6, `specs/10`.
> Замер (2026-07-19, native, testgen-корпус 24k × dim 384, k=8 — ровно
> порог `flat_to_hnsw`): `vec/flat_24k_d384_k8` = **332 мкс** — бюджет
> < 1 мс держится с трёхкратным запасом.

Конфиг: `dim` (0 = слой выключен; ≤ 4096), метрика cosine — векторы
нормализуются при приёме, дальше только dot product.

Хранение (всё — DynArena/плоские секции):

- `vec_i8`: слот = `dim` × i8 + `scale f32` (симметричная квантизация:
  `scale = max|x|/127`, `q = round(x/scale)`). Потеря ~1–2% recall — принято.
- `sigs`: бинарные сигнатуры 1 бит/изм., упакованы в u64-слова (48 Б при 384d) —
  пре-фильтр.
- f32 не хранится нигде (паспорт ёмкости).

Квантизация происходит **до** журнала (в журнале уже i8+scale) — реплей
детерминирован и не требует float-воспроизводимости.

### Поиск, фаза 1 — Flat (до порога)

1. Хэмминг-скан сигнатур запроса по всем живым (popcount по u64, автовекторизуемо,
   SIMD128-дружелюбно): top `R = max(4·k, 256)` кандидатов.
2. Рескоринг R кандидатов i8-dot (i16→i32 аккумуляция) → точный top-k.

Числа (см. 00): @10k — десятки мкс; @100k скан сигнатур ~5 МБ → ~0.5 мс —
предел бюджета, отсюда порог.

### Поиск, фаза 2 — HNSW (за порогом ~24k, число уточняет бенч)

- Параметры: M = 16, M0 = 32, ml = 1/ln(2)... стандартная геометрия уровней;
  `ef_construction = 200`, `ef_search` default 64 (перекрывается в запросе).
- Хранение: level0 — фиксированные слоты 32 соседа × u32 (128 Б) в DynArena;
  верхние уровни — ChunkPool-списки; entry point + счётчики в заголовке.
- Дистанция внутри графа — i8-dot по `vec_i8` (сигнатуры в HNSW не участвуют).
- Вставка инкрементальная (однопоточная, ~1–3 мс на вектор при 200 ef — это
  внутри бюджета remember? **нет**: помечаем — вставка в HNSW амортизируется:
  новые векторы падают в flat-«хвост» (скан), в граф вливаются пачкой в
  `maintain()`; recall ищет в графе и хвосте, сливает). Это решение снимает
  худший случай remember.
- Удаления: tombstone; при доле мёртвых > 10% `maintain` пересобирает граф.
- Переключение Flat → HNSW: автоматически в `maintain()` при превышении порога
  (сборка графа — bulk, с прогрессом в отчёте).

`VectorIndex` — enum `{ Flat, Hnsw { graph, flat_tail } }` за общим
интерфейсом `search(query_i8, k, ef, allow: &Bitmap) -> TopK`.

## 6. Графовое расширение

Из запроса извлекаются якоря-сущности (упомянутые имена → EntityId через
интернер + явный параметр `entities`). Расширение:

- глубина ≤ 2 (Config), обход по out/in-аренам range-сканами;
- собираются: факты соседних сущностей (entity → facts индекс), provenance-факты
  пройденных рёбер;
- вес кандидата = `w_graph · decay^depth` (decay = 0.5), плюс сам список рёбер
  идёт в результат recall (агенту полезно видеть связи, не только факты).

Бюджет обхода жёсткий: ≤ 64 сущностей, ≤ 256 фактов-кандидатов, ≤ 128 рёбер
в результат, и **≤ 2048 просмотренных постинг-записей** (реализация:
хаб-сущность с 14k фактов не должна превращать обход в полный декод её
списка — бюджет на работу, не только на кандидатов).

## 7. Слияние: hybrid recall

Вход `RecallQuery` (см. `05-api.md`): text?, vector?, tags[], entities[],
временные параметры, k, token_budget.

Пайплайн (скретч-буферы переиспользуются, аллокаций нет — инвариант):

1. Фильтры-множества: теги ∩ live ∩ as_of → битовая карта allow (если тегов
   нет — только live ∩ as_of, лениво).
2. Источники (каждый отдаёт ранжированный список ≤ 128):
   - BM25 (если есть text),
   - вектор (если есть vector),
   - граф (если есть якоря),
   - временной range (если задан range) — ранжирован свежестью.
3. **RRF**: `score(f) = Σ_источники w_s / (60 + rank_s(f))`; веса w_s из Config
   (default 1.0 каждому). Простая, устойчивая, безнастроечная формула — тюнинг
   скоров источников друг под друга не нужен.
4. Recency-буст: `score ·= 1 + w_rec · 2^(-(now - recorded_at)/half_life)`
   (default half_life 180 дней, w_rec 0.25) — свежее при прочих равных выше.
5. Дедуп по цепочке ревизий: из цепочки — только последняя валидная версия
   (с `include_closed` — вся цепочка, помеченная интервалами).
6. Отбор в бюджет: жадно по score, оценка стоимости факта = len(text)/4 + 8
   токенов накладных; стоп по k и token_budget.
7. Сборка результата: структурный (`Vec<RecalledFact>`: id, score, источники,
   интервалы, рёбра) + рендер компактного блока текста (шаблон в `05-api.md`).

## План тестов

- Токенизатор: таблица юнит-кейсов (рус/eng/цифры/эмодзи/CJK/пусто/64Б+),
  property: конкатенация с разделителем не меняет мультимножество токенов.
- BM25: эталонные скоры на мини-корпусе, посчитанные независимым скриптом
  (testdata, python-эталон в репо не входит — только числа); монотонность idf.
- Векторы: квантизация — ошибка dot(i8) vs dot(f32) < 3% на случайных парах;
  recall@10 flat-поиска по сигнатурам+рескорингу ≥ 0.95 против brute-force f32
  на синтетике testgen; HNSW recall@10 ≥ 0.9 (ef=64) — гейт.
- Граф: обход с хабом (сущность с 10k рёбер) укладывается в бюджет обрезки.
- Hybrid: сценарные тесты «источники согласны/противоречат», отсутствие каждого
  из источников; property — результат ⊆ allow-набора; детерминизм (два recall
  подряд идентичны).
- Все — и нативно, и под wasmtime (cargo test --target + wasmtime runner в CI).
