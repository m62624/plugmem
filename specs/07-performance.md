# 07 — контракт производительности и качества

> «Быстро» — это число в таблице и гейт в CI, а не прилагательное в README.
> Здесь: бюджеты, механика измерения, генератор корпусов, мандат покрытия,
> fuzz/miri, состав CI.

## 1. Бюджеты латентности (контракт)

Корпуса: S = 10k фактов, M = 100k (дизайн-центр), L = 1M (потолок wasm32).
Все числа — однопоточно; native = современный x86-64 десктоп, wasm = wasmtime
на той же машине. p50 / p99 после прогрева.

| Операция | M native | M wasm | L native | Прим. |
|---|---|---|---|---|
| `remember` (без embed) | < 500 мкс / 2 мс | < 1.5 мс | < 1 мс | вкл. полную similar-детекцию (entity+лексика+вектор) и журнал без fsync; с `skip_similar` — < 100 мкс |
| `recall` структурный (BM25+теги+время+граф) | < 200 мкс / 1 мс | < 600 мкс | < 1 мс | k=8, budget 512 |
| `recall` + вектор (Flat, ≤ порога) | < 500 мкс | < 1.5 мс | — | |
| `recall` + вектор (HNSW) | < 500 мкс | < 1.5 мс | < 1 мс | ef=64 |
| `get(id)` | < 2 мкс | < 5 мкс | < 2 мкс | |
| cold open (снапшот) | чтение файла + < 5 мс | memcpy + < 5 мс | + < 20 мс | валидация O(метаданных) |
| `snapshot()` | < 50 мс | < 100 мс | < 500 мс | без fsync |
| `maintain` полный | < 1 с | < 3 с | < 10 с | единственная O(база) операция |

Бюджет памяти: коэффициент раздува «RAM-образ / полезные данные» ≤ 1.6
(слоты+метаданные+индексы против суммы текстов и векторов); проверяется
тестом на корпусе M.

Бюджет размера wasm-артефакта: **≤ 1 МиБ** raw после wasm-opt `-Oz`
(CI-гейт; фиксируем и отслеживаем — раздувание бинаря почти всегда значит
случайную мономорфизацию или лишнюю зависимость).

Числа при первом прогоне бенчей могут быть ужесточены (только вниз —
ослабление потолка = осознанное решение с записью в этот файл).

**Фактические замеры на testgen-корпусе (native, 2026-07-20)** — и два
осознанных пересмотра:

| Бенч | Число | Прим. |
|---|---|---|
| `recall/structural_100k` | 471 мкс | текст (3 терма, df≈5k) + **хаб-якорь** графа |
| `recall/tags_and_range_100k` | 226 мкс | тег + окно ~5k операций |
| `vec/flat_24k_d384_k8` | 332 мкс | ровно порог flat→HNSW |
| `hnsw/search_30k_d384_k8_ef64` | 185 мкс | граф + пустой хвост |
| `bm25/search_3_terms_of_10k` | 64 мкс | Σdf = 1399 |
| `idlist/intersect_3_tags_of_100k` | 51 мкс | селективности 10/5/2% |
| сборка HNSW (maintain) | ~1.6 мс/вектор | 48 с на 30k×384; одноразово |

1. **Пересмотр потолка структурного recall: ≤ 600 мкс typ @M** (было
   200 мкс). Прежние 61 мкс мерились на корпусе без хабов; testgen-корпус
   даёт Zipf-хаб как якорь → графовый источник честно выедает свой бюджет
   `GRAPH_EXAMINE_CAP` = 2048 постингов, плюс BM25 с df≈5k. Это цена
   заявленных капов, не регрессия сложности (счётчики-гейты стоят).
   Кандидат-оптимизация v1.1 (записано): `doc_len` из арены → плоская
   таблица `fact→len` (пряморазыменование вместо бинарного поиска на
   каждый постинг).
2. **`maintain` с полной сборкой HNSW — вне бюджета < 1 c** и не
   пытается в него влезть: сборка ~1.6 мс/вектор происходит один раз при
   пересечении `flat_to_hnsw` (или >10% мёртвых узлов); steady-state
   maintain несёт граф через remap (O(рёбер), миллисекунды) + вставку
   хвоста. Политика обёрток должна знать: «первый maintain за порогом —
   долгий».

## 2. Инвариант нулевых аллокаций

`recall` и `get` после прогрева: **0 обращений к аллокатору** (скретчи
переиспользуются, рост скретчей — только на новых максимумах размеров).
Механика: тест-харнесс с глобальным counting-allocator; эталонный сценарий на
корпусе M; assert 0. `remember`: ≤ 8 аллокаций (амортизированные росты пулов
не в счёт — считаются отдельным счётчиком).

## 3. Детерминированные счётчики работы (CI-гейты)

Wall-clock в CI лжёт; гейты — на счётчиках (feature `counters`, в release-бенчах
выключена):

| Счётчик | Откуда |
|---|---|
| `cmp_ops`, `bytes_shifted`, `pages_walked`, `splits` | арена |
| `postings_decoded` | BM25 |
| `dist_evals`, `sig_words_scanned` | векторы |
| `edges_walked`, `entities_visited` | граф |
| `alloc_count`, `alloc_bytes` | тест-аллокатор |

Гейт-тесты (`tests/perf_gates.rs` в core, паттерн elenchus): фиксированный
seed testgen-корпуса → эталонные операции → assert «счётчик ≤ потолок».
Потолки заполняются при первой реализации измерением ×1.2 запаса и с тех пор
охраняют сложность: регрессия алгоритма (случайно квадратичный проход,
разросшийся скан) валит PR на любом железе одинаково.

## 4. Criterion-бенчи (информационные)

`benches/` в arena и core; прогон локально и по PR-лейблу `benchmark`
(не гейт). Матрица: операции бюджетной таблицы × S/M/L × native/wasmtime.

Механика разделения (решено): criterion-бенчи и так opt-in — `cargo test` их
не запускает, исполняет только явный `cargo bench` (CI зовёт его лишь в
бенч-джобе). Отдельный feature для них не нужен; если бенчам понадобится
доступ к внутренностям — приватные API открываются через
`#[cfg(feature = "bench-internals")]`, а бенч-таргет получает нативное
`[[bench]] required-features = ["bench-internals"]`. Перф-гейты — другое:
это обычные тесты за feature `counters` (`cargo test --features counters`),
они в CI обязательны.
Отдельно: микробенчи арены (см. `01`), квантизация, hamming-скан, RRF-слияние.
Результаты складываются в `bench-history/` (json) — тренд руками.

## 5. Сравнительный харнесс («мы против них»)

Отдельный не-CI проект `bench-compare/` (native): общий корпус M →
plugmem vs tantivy (BM25), vs sqlite-fts5, vs qdrant-local (векторы,
через их API — с честной пометкой про сетевой пол). Метрики: латентность
recall/insert, RAM, размер на диске, cold start. Цель — публикуемая таблица в
README и честная проверка слова «не уступаем». Обновляется на релиз.

## 6. Генератор корпусов (`plugmem-testgen`)

Детерминирован по seed (никакого рандома без seed в тестах — общий закон
репо). Параметры: N фактов; словарь 30k термов, Zipf s≈1.07; длина текста
норм. распределение μ=150; сущности ~5% N со степенным распределением
популярности (хабы существуют!); теги 1–4 из Zipf-пула 500; рёбра ~3/факт;
временная ось: 2 года, плотность растёт к «сегодня»; ревизии: 10% фактов
имеют цепочку 2–4; векторы: 64 гауссовых кластера на единичной сфере +
шум (проверяет и recall семантики, и квантизацию). API: `Corpus::generate(seed,
size) -> impl Iterator<Item = Op>` (операции, не состояние — прогоняются
через публичный API).

## 7. Покрытие и корректность — мандат

- **Покрытие**: цель — 100% исполнимых строк для `plugmem-arena` и
  `plugmem-core`; **жёсткий гейт — не ниже 90%** (решение пользователя:
  tarpaulin не все конструкции атрибутирует корректно). Tarpaulin помечает
  часть неисполнимых строк как «непокрытые» (поля struct-литералов, строки
  вызова макросов, атрибуты, const-свёрнутые ветки) — такие строки в отчёте
  **аудируются руками на ревью** (проверяется, что окружающий statement
  исполняется тестом), а не списываются молча. Обёртки: ≥ 90%. Всегда в
  связке: `cargo fmt` + `cargo clippy` (0 предупреждений) перед каждым
  коммитом.
- **Property-тесты (proptest)** — на каждую структуру эквивалентность
  референс-модели (перечислены в спеках 01–04).
- **miri** — весь plugmem-arena + unsafe-пути core, еженедельный полный прогон
  + обязательный на PR, трогающий unsafe. Механика: miri — интерпретатор MIR
  (замедление ×100–500), поэтому объёмные сдвиговые стресс-тесты помечены
  `#[cfg_attr(miri, ignore)]` (UB-пути покрыты малыми тестами тех же ветвей).
  Property-тесты под miri тоже игнорируются: харнесс proptest ходит в ОС
  (getcwd для persistence упавших кейсов), что запрещено изоляцией miri.
- **Fuzz (cargo-fuzz, nightly job)**: снапшот-загрузчик (произвольные байты →
  только Err), журнал-реплей, токенизатор, разбор RecallQuery из MCP.
  Любая паника/UB из fuzz = P0-баг.
- **Кросс-таргет**: весь тест-сьют core — нативно и под wasmtime;
  `cargo build --target wasm32v1-none` для библиотек — гейт.
- Паритет поверхностей (cli/mcp/wasm) — сценарные тесты из `06`.

## 8. Состав CI (PR-гейты)

1. fmt + clippy (deny warnings) — весь workspace, **матрица фич** для
   библиотек: `default` / `--no-default-features` /
   `--no-default-features --features counters` / `--features counters`
   (проверено руками 2026-07-18: все 4 комбинации по нулям; фичи меняют
   набор компилируемого кода, clippy одной комбинации не ловит остальные).
2. Тесты native (stable) + доктесты — тоже в обеих feature-конфигурациях
   (`default` и `--features counters`).
3. Тесты core под wasmtime; build `wasm32v1-none`.
4. Perf-гейты (счётчики) — корпус S в PR (быстро), M — в merge-queue/nightly.
5. Zero-alloc тест.
6. Покрытие с порогом (100/100/90).
7. cargo-deny (лицензии/дубликаты/advisories).
8. Nightly: miri, fuzz (короткие сессии), бенчи M/L, wasm-npm smoke.
