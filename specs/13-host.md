# 13 — plugmem-host: файловый слой и оркестрация доступа

> Дизайн-решения зафиксированы 2026-07-20 (Fable, карт-бланш пользователя:
> «host должен быть максимально удобным; реши вопрос мультиклиентности
> профессионально, как это делают в БД»). **Реализовано 2026-07-20, в тот
> же день**: 12 интеграционных тестов (включая мок-HTTP эмбеддер, flock,
> 4 потока на одном хэндле, 7 битых ответов сервера), покрытие файлов
> 90–100%, README крейта написан. Отклонение от §4: сигнатура `Embedder`
> возвращает `HostError` (единый тип слоя) вместо отдельного `EmbedError`
> из specs/05. Host — часть Rust-опыта («указал файл и поехали»), а не
> обёртка для не-Rust потребителей (те — CLI/MCP/wasm, этап 5).

## 0. Состав крейта

1. `FileStorage` — реализация `plugmem_core::Storage` поверх двух файлов.
2. `Database` — главный тип: движок + файл + политика обслуживания за
   одним замком; клонируемый хэндл (`Arc`), безопасный для потоков.
3. `Embedder` — трейт из specs/05 + две реализации:
   `OpenAiCompatEmbedder` и `NullEmbedder`.
4. `HostError` — типизированные ошибки слоя.

## 1. Модель конкурентности (главное решение)

Ядро — однопоточный single-writer по построению (specs/00 §4). Host не
пытается это «улучшить» — он это **честно оркеструет** на трёх уровнях:

| Уровень | Механизм | Поведение |
|---|---|---|
| **Один файл, несколько процессов** | эксклюзивный advisory-lock ОС на `<base>.lock` (std `File::try_lock`, стабилен с Rust 1.89 — без новых зависимостей) | второй процесс получает `HostError::Locked` **сразу**, без ожидания. Честный отказ вместо тихой порчи — модель SQLite-мира: одна база = один процесс-владелец |
| **Один файл, несколько потоков/агентов одного процесса** | `Database` = `Arc<Inner>`, состояние движка за `Mutex`; хэндл `Clone + Send + Sync` | все глаголы сериализуются на мьютексе. При микросекундных операциях ядра это сотни тысяч оп/с — очередь, а не бутылочное горлышко. Две модели, пишущие в один файл, просто клонируют хэндл |
| **Разные файлы** | независимые `Database` | полный параллелизм: разные мьютексы, разные lock-файлы. Две модели → два файла → ноль контенции. «Менеджер баз» не нужен как тип — открывайте столько `Database`, сколько файлов |

Кооперативные схемы (ожидание чужого lock, многопроцессный журнал,
read-реплики поверх zero-copy снапшота) — осознанно вне v1; двери
оставлены (снапшот уже read-only-shareable по формату).

**Правило сети вне замка.** Всё дорогое и внешнее — вычисление
эмбеддинга по HTTP — происходит **до** захвата мьютекса. Пока один агент
ждёт эмбеддер, другие читают и пишут базу. Критическая секция содержит
только микросекундные вызовы ядра (+ fsync по политике).

## 2. FileStorage

Раскладка при `base = "agent.plugmem"`:

| Файл | Роль |
|---|---|
| `agent.plugmem` | снапшот (образ движка) |
| `agent.plugmem.journal` | append-only журнал после снапшота |
| `agent.plugmem.lock` | пустой lock-файл (advisory) |
| `agent.plugmem.tmp` | временный при атомарной записи снапшота |

- `write_snapshot`: tmp → `fsync(tmp)` → `rename` поверх снапшота →
  `fsync` каталога (unix). Читатель никогда не видит полуфайл.
- `append_journal`: `O_APPEND` + `write_all`; fsync — по политике.
- `clear_journal`: truncate + fsync.
- Политика fsync (`FsyncPolicy`): `EachOp` (default — durability каждой
  операции; цена измерена и принята) | `OnSnapshot` (быстрее, окно
  потери = хвост журнала при падении ОС).
- Lock берётся в `open`, живёт до `Drop` (закрытие fd снимает его даже
  при аварийном завершении — свойство advisory-lock ОС).
- **Версионированный MVCC (обновлено 2026-07-27).** Read-write `open` берёт
  **эксклюзивный** writer-lock на `*.lock` (`try_lock`) — только против других
  писателей (второй писатель → `Locked` сразу, без ожидания). **Читатели
  writer-lock НЕ берут:** `open_readonly` (specs/16) **пинит текущее
  поколение** снапшота разделяемым локом на самом файле `*.snap.<N>`
  (`try_lock_shared`) и мапит его. Поколения иммутабельны (checkpoint пишет
  новое, старое не перезаписывает), поэтому **писатель и N читателей работают
  одновременно** — межпроцессно, без блокировки и без торна. Модель WAL/MVCC,
  не «N читателей ИЛИ писатель». GC старого поколения — pin-aware: писатель
  удаляет его только когда `try_lock` (exclusive) на нём проходит (нет
  читателей-пиннеров). Читатель видит «на момент последнего checkpoint»
  (snapshot-isolation; reopen, чтобы увидеть новее).

## 3. Database — политика обслуживания

`Database::open(path, Config)` / `Builder` с настройками:

| Ручка | Default | Смысл |
|---|---|---|
| `fsync` | `EachOp` | см. выше |
| `snapshot_every_ops` | 1024 | авто-`snapshot` после N мутаций |
| `snapshot_journal_bytes` | 4 МиБ | …или когда журнал разросся |
| `maintain_every_forgets` | `None` | опц.: авто-`maintain` после N forget'ов (проверка на границе снапшота) |

Авто-снапшот срабатывает **внутри той же критической секции**, что и
вызвавшая его операция — очередной вызывающий просто чуть дольше ждёт
мьютекс; фоновых потоков нет (принцип ядра). `maintain` по умолчанию
только явный (`db.maintain()`): первый maintain за порогом HNSW платит
сборку графа (~1.6 мс/вектор, specs/07) — это решение владельца
процесса, не тихая пауза.

Глаголы `Database` зеркалят ядро (`remember/recall/revise/forget/link/
get/stats/maintain/checkpoint`) с двумя удобствами:

1. **Авто-эмбеддинг**: если сконфигурирован `Embedder`, `remember` без
   `vector` эмбеддит текст, `recall` с текстом и без вектора эмбеддит
   запрос — оба **до** захвата замка. Явно переданный вектор всегда
   уважается; `NullEmbedder`/отсутствие эмбеддера = чисто структурная
   база (полноценна by design).
2. Владение входами: публичные методы принимают `&str`/срезы как ядро —
   без копий сверх необходимых.

**Целостность и восстановление (specs/16 §9 вехи G+H).** Сверх зеркальных
глаголов host добавляет: `verify()` (контентная согласованность),
`ReadOnlyDatabase::scrub()` (байтовая целостность контейнера, резюмируемый
итератор под shared-локом) и `recover(src, dst, cfg, now)` (Tier-2 salvage:
выкинуть контентно-битые факты, записать чистую копию, src сохранён). `recover`
и `maintain` — **disk-first**: большие пулы (векторы, текст) стримятся через
temp-`Scratch`, в RAM только метаданные + HNSW-граф, поэтому пересборка не
ограничена размером образа. Дефолт открытия — trust/sparse (не чек-суммит образ).

## 4. Embedder

Трейт — как в specs/05 (`dim()`, батчевый `embed`).

**Решение: нативного Ollama-клиента НЕ делаем.** Ollama, LM Studio,
vLLM, llama.cpp-server, OpenAI, OpenRouter и т.д. говорят на одном
OpenAI-совместимом `/v1/embeddings` — один `OpenAiCompatEmbedder`
покрывает всех (для Ollama: `base_url = "http://localhost:11434/v1"`).
Отдельный клиент был бы вторым кодом ради того же JSON.

`OpenAiCompatEmbedder::new(base_url, model, dim)` + `.with_api_key(...)`:
`dim` задаётся явно (детерминизм и отсутствие стартового сетевого
вызова; несовпадение с ответом сервера — типизированная ошибка).
HTTP — `ureq` (блокирующий, маленький; ядро синхронно, async в цепочке
не нужен), JSON — `serde_json`.

Локальный встроенный эмбеддер (candle, e5-small) — v1.1, как и было в
specs/05.

## 5. Ошибки

```rust
#[non_exhaustive]
pub enum HostError {
    Locked { path },      // база занята другим процессом/хэндлом
    Io { path, source },  // файловая операция
    Engine(plugmem_core::Error),
    Embed(String),        // транспорт/формат ответа эмбеддера
}
```

## 6. План тестов (мандат ≥ 90%)

- FileStorage: roundtrip open→remember→drop→reopen (реплей журнала);
  checkpoint → снапшот на диске, журнал пуст; tmp-файл не выживает;
  обрыв хвоста журнала (дописать мусор) → открытие с `truncated_tail`.
- Lock: второе `open` того же файла → `Locked` (и из того же процесса —
  advisory-lock на отдельном fd этого не позволяет тоже); после `drop`
  первого — открывается.
- Политика: `snapshot_every_ops = N` → после N мутаций журнал пуст;
  `maintain_every_forgets` срабатывает.
- Embedder: мок-сервер на `std::net::TcpListener` (никакой сети в CI):
  корректный ответ → векторы; неверная размерность/битый JSON/не-200 →
  `Embed`-ошибка; авто-эмбеддинг end-to-end (remember текста → recall
  по смыслу через мок-векторы).
- Конкурентность: несколько потоков на клонах одного `Database` — все
  операции успешны, число фактов сходится, дедлоков нет.
- Все временные файлы — в уникальных поддиректориях `std::env::temp_dir`,
  подчищаются.
