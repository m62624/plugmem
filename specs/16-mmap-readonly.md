# 16 — mmap zero-copy read-only open (Cow-backing)

> **Статус: реализовано 2026-07-20.** Все три этапа (§7) сделаны и
> зелёные (fmt + clippy ×4 + тесты ×2 + wasm32v1-none build ×2 +
> wasm32-wasip1 сьют ×2). Настоящий zero-copy read-only путь, при
> котором база не грузится в RAM целиком, а страницы подгружаются ОС по
> обращению. Жёсткое ограничение пользователя: **`plugmem-arena`
> остаётся `no_std` и без единой новой зависимости** — соблюдено
> (заимствование через `alloc::borrow::Cow`, `std`/`memmap2` заперты в
> `plugmem-host`). Self-reference в host решён вариантом 2 (`self_cell`,
> §4): единственный `unsafe` на read-only пути — сам вызов mmap; сам
> borrow остаётся safe. Кросс-OS CI (Linux/Windows/macOS) — приёмочный
> сигнал держащей mmap семантики — запускает владелец.

## 0. Суть решения (TL;DR)

Сегодня `Memory` **владеет** своими байтами: каждая плоская структура
держит `pool: Vec<u8>`, а `load` делает `pool.to_vec()` — при открытии
весь файл копируется в арены. Для базы 8 ГиБ это 8 ГиБ RAM. Цель —
открыть большую (memory64-класса) базу так, чтобы резидентными были
**только реально прочитанные страницы**.

Единственный способ этого добиться — структуры должны **заимствовать**
байты из отображённого файла, а не копировать. Реализуется одним
приёмом: `pool: Vec<u8>` → `pool: Cow<'a, [u8]>`.

- **owned-путь** (всё как сейчас: `new`/`open`/`from_bytes`, запись,
  журнал, снапшот, maintain) — `Cow::Owned`, поведение **байт-в-байт
  неизменно**;
- **borrowed-путь** (новый `open_readonly`) — `Cow::Borrowed(&mmap[..])`,
  копий нет, мутации запрещены на уровне хэндла;
- мутация borrowed-структуры (если бы случилась) — `Cow::to_mut()`
  автоматически поднимает в `Owned` (copy-on-write); в v1 read-only
  хэндл write-глаголов не имеет, поэтому CoW на практике не срабатывает —
  это лишь страховка типа.

`memmap2` — единственная новая зависимость, **только в `plugmem-host`**.

## 1. Что именно заимствуем, а что нет

Заимствования достойны только **большие** секции — байтовые пулы, чей
размер растёт с объёмом данных. Мелкие метаданные (индексы страниц,
таблицы) масштабируются со структурой, а не с контентом, и
восстанавливаются из образа при load дёшево — их **оставляем owned**
(rebuild в `Vec`, как сейчас). Для базы 8 ГиБ метаданные — десятки МБ,
это несущественно.

| Структура | Заимствуем (`Cow<'a,[u8]>`) | Остаётся owned (`Vec`) |
|---|---|---|
| `RawArena` | `pool` (страницы, 4 КиБ каждая) | `heads`, `next`, `counts` |
| `BlobHeap` | `pool` (байты блобов) | `index: Vec<(u32,u32)>` |
| `ChunkPool` | `pool` (чанки по 64 Б) | `used` |
| `Interner` | `heap.pool` (через `BlobHeap`) | `table: Vec<u32>` |
| `VecPool` (core) | `bytes` (квантованные слоты) | — |

Следствие: лайфтайм `'a` появляется в типах `Arena<'a,T>`,
`BlobHeap<'a>`, `ChunkPool<'a>`, `Interner<'a>`, `VecPool<'a>` и
`Memory<'a>`. owned-конструкторы дают `'static`
(`Cow::Owned` валиден при любом `'a`), поэтому весь существующий код —
это `Memory<'static>`.

## 2. Почему arena остаётся no_std и без зависимостей

`Cow<'a, [u8]>` живёт в **`alloc::borrow`**, не в `std`. Ни атомиков
(в отличие от `Arc`, который сломал бы `wasm32v1-none`), ни `memmap2`,
ни `std`. Изменение arena — **чисто на уровне типов/API**:

```rust
pub struct BlobHeap<'a> {
    pool: Cow<'a, [u8]>,
    index: Vec<(u32, u32)>,
    cfg: BlobHeapCfg,
}

impl<'a> BlobHeap<'a> {
    // Существующий owned-load: копия, как сейчас. Возвращает 'static.
    pub fn load(cfg, index: &[u8], pool: &[u8]) -> Result<BlobHeap<'static>, Error> {
        // ... pool.to_vec().into()
    }
    // Новый borrowed-load: без копии, привязан к 'a.
    pub fn load_borrowed(cfg, index: &[u8], pool: &'a [u8]) -> Result<BlobHeap<'a>, Error> {
        // ... Cow::Borrowed(pool); валидация та же
    }
    fn bytes(&self) -> &[u8] { &self.pool }         // все чтения
    fn pool_mut(&mut self) -> &mut Vec<u8> { self.pool.to_mut() } // все записи (CoW)
}
```

Граница зависимостей:

| Крейт | Изменения | std? | новые deps |
|---|---|---|---|
| `plugmem-arena` | `+ 'a`, `Cow`-backing, `*_borrowed`-конструкторы | **нет** | **ноль** |
| `plugmem-core` | `Memory<'a>`, `from_bytes_borrowed`, `VecPool<'a>` | нет | ноль |
| `plugmem-host` | `Mmap`-владение, `open_readonly`, self-ref glue | да (и так) | **`memmap2` — тут** |

## 3. Контракт `Database::open_readonly` (host)

```rust
impl Database {
    /// Открывает базу только для чтения поверх mmap: секции ядра
    /// заимствуют отображённые байты, ОС подгружает лишь тронутые
    /// страницы. Требует checkpoint'нутую базу (пустой журнал).
    pub fn open_readonly(path) -> Result<ReadOnlyDatabase, HostError>;
}
```

- **Только чтение.** `ReadOnlyDatabase` несёт лишь `recall`/`get`/`stats`
  (+ `path`, `Debug`). Никаких `remember/revise/forget/link/maintain/
  snapshot/checkpoint` — на замапленных байтах писать нельзя, а CoW-подъём
  целой арены свёл бы zero-copy на нет.
- **Требует пустой журнал.** Реплей журнала мутирует структуры → CoW
  скопировал бы целую арену. Поэтому непустой журнал → типизированная
  ошибка `HostError::NeedsCheckpoint { path }` с подсказкой «открой
  read-write один раз, чтобы сделать checkpoint». (Overlay-журнал без
  копирования базы — открытый вопрос v2, §7.)
- **Блокировка — shared-lock (реализовано 2026-07-21).** `open_readonly`
  берёт **разделяемый** advisory-lock (`File::try_lock_shared`): несколько
  read-only хэндлов — в одном процессе или в разных — маппят файл
  одновременно. Shared-lock исключает любого exclusive-владельца (писателя),
  поэтому файл не может измениться под живым читателем — это и есть аргумент
  безопасности mmap (см. §5). Модель как у SQLite: N читателей ИЛИ один
  писатель.
- **Windows-семантика.** Пока файл замаплен, ОС не даёт его
  переписать/переименовать. Для read-only это естественно (мы не пишем);
  для этого хэндл и держит lock — записи со стороны быть не может.

## 4. Self-reference в host (ядра не касается)

`ReadOnlyDatabase` держит и `Mmap`, и `Memory<'a>`, заимствующий его —
самоссылающаяся структура. Решается **в host**, тремя способами (выбор
при реализации, приоритет — минимум unsafe и минимум deps):

1. **owning-ref с одним `unsafe`** — держим `Mmap`, а `Memory<'static>`
   строим из `&'static [u8]`, полученного transmute'ом лайфтайма;
   `Mmap` в той же структуре гарантирует, что байты живы дольше
   `Memory`. Один задокументированный `unsafe` в host, ноль новых deps.
2. **`self_cell` — выбрано.** Безопасно, +1 dep (std, приемлемо). Так
   единственный `unsafe` на read-only пути — сам (неизбежный) вызов
   mmap; borrow остаётся safe, что соответствует духу проекта (весь
   lifetime-рефакторинг ядра делался именно ради ухода от unsafe
   self-reference). `Mmap` — owner, `Memory<'a>` — covariant dependent;
   `try_new` строит движок фейлибельно (`Memory::from_bytes_borrowed`).
   `ReadOnlyDatabase` держит `Mutex<MappedMemory>` (recall переиспользует
   scratch → `&mut Memory`; Mutex же даёт `Send + Sync`), `FileStorage`
   (держит эксклюзивный lock всю жизнь хэндла) и `path`.
3. `Box::leak(Mmap)` → `&'static` — просто, но течёт на время процесса;
   годится только если хэндл живёт до конца процесса. Отвергнуто.

`self_cell` сам гарантирует drop dependent раньше owner, так что порядок
полей руками выдерживать не нужно.

## 5. Безопасность mmap (это `unsafe` по природе)

Все file-backed конструкторы `memmap2` — `unsafe`: если файл усечь или
переписать под нами, обращение к отображённой памяти даёт SIGBUS (Unix)
/ исключение (Windows) — краш процесса. Наш аргумент корректности:

- `open_readonly` держит **разделяемый advisory-lock** на весь срок
  жизни хэндла → ни один кооперативный писатель (exclusive-lock) базу не
  тронет; остальные держатели — только читатели, которые лишь читают;
- shared исключает exclusive (specs/13) → второго писателя нет;
- сторонний `truncate`/`rm` файла базы под живым хэндлом — **вне
  контракта**, ровно как порча любого файла БД под работающим движком;
  это документируется, а не «защищается».

Единственный `unsafe`-путь mmap — в host (std); ядро и arena остаются
без нового unsafe. `arena.rs:857` (uninit-страницы) не трогаем.

## 6. Платформенная матрица

`memmap2` 0.9.11: MSRV 1.63, MIT/Apache-2.0, кросс-платформенный —
покрывает все наши таргеты (linux/macos/windows × x86_64/aarch64).
`memmap` (оригинал) — **не брать** (RUSTSEC-2020-0077, unmaintained).

| Проверка | Ожидание |
|---|---|
| open_readonly + recall/get на каждой ОС | одинаковый результат, что owned-open |
| held-map при попытке записи (Windows) | write невозможна (lock + read-only хэндл), не краш |
| Drop хэндла → файл снова записываем | да, на всех ОС |
| foreign truncate под хэндлом | вне контракта (не тестируем как «должно работать») |

Кросс-OS CI (запускает владелец) — главный приёмочный сигнал: held-map
семантика различается Unix/Windows, и job на трёх ОС это выявит.

## 7. План реализации (этапы; каждый — зелёные ворота + коммит)

Ворота на каждом шаге: `fmt` + clippy ×4 + тесты ×2 + `wasm32v1-none`
build + wasm32-wasip1 сьют (specs/11 §5, specs/15). owned-путь обязан
остаться **байт-в-байт** (canonical snapshot, детерминизм).

1. **arena — Cow-backing (no_std, 0 deps).** Добавить `'a` и
   `Cow<'a,[u8]>` в `RawArena`/`BlobHeap`/`ChunkPool`/`Interner`;
   `*_borrowed`-конструкторы; чтения через `bytes()`, записи через
   `to_mut()`. Существующие `load` возвращают `'static`. Тесты arena
   зелёные без правок логики; +тест borrowed-load ≡ owned-load
   (структурная эквивалентность) на каждой структуре.
2. **core — `Memory<'a>` + `VecPool<'a>`.** Протянуть лайфтайм;
   `from_bytes_borrowed(snapshot: &'a [u8], cfg) -> Memory<'a>`
   (журнал пуст — иначе ошибка); owned-конструкторы = `Memory<'static>`.
   Паритет-тест: `recall`/`get`/`stats`/`rendered` борроу-открытия
   идентичны owned-открытию того же снапшота (байты rendered равны).
3. **host — `memmap2` + `open_readonly`.** `Mmap`-владение, self-ref
   (§4), `ReadOnlyDatabase` (recall/get/stats/path/Debug), lock как
   у read-write, `NeedsCheckpoint` при непустом журнале. Тесты §8.

## 8. План тестов

- **owned не регрессирует:** весь текущий сьют зелёный без изменений
  ожиданий (тип сменился, поведение — нет).
- **borrowed ≡ owned (arena):** для каждой структуры
  `load(...).структурно_равно(load_borrowed(...))`.
- **borrowed ≡ owned (core):** один снапшот открыт обоими путями →
  `recall`/`get`/`stats` и байты `rendered` совпадают на наборе запросов.
- **CoW-страховка:** искусственно мутировать borrowed-структуру →
  `to_mut()` поднимает в `Owned`, исходные mmap-байты не изменены
  (unit в arena).
- **host open_readonly:** checkpoint'нутая база открывается readonly,
  recall совпадает с read-write; непустой журнал → `NeedsCheckpoint`;
  Drop → файл записываем снова.
- **shared-lock (реализовано 2026-07-21):** N read-only хэндлов маппят
  один файл одновременно (все отвечают идентично); живой читатель отбивает
  писателя (`Locked`), живой писатель отбивает читателя; после снятия всех
  читателей писатель открывается снова.
- **кросс-OS:** те же host-тесты в CI-матрице (linux/windows/macos).
  Держим в уме held-map различия — Windows не даёт переписать замапленный
  файл, поэтому read-only хэндл и lock согласованы.

## 9. Планируемое v2 и открытые вопросы

**Цель (явно, раньше висела как YAGNI): ни чтение, ни запись не требуют
полной загрузки базы в RAM — модель SQLite (spec 00).** Read-путь достиг
её ещё в §1–§8 (mmap, borrowed-арены). Write-путь закрыт в два захода:
**M1 (ядро)** и **M2 (host)** — оба реализованы (см. ниже). Осталась одна
доработка до **полной** SQLite-модели — ленивая валидация (**веха F**),
тоже описана ниже.

- **Overlay на запись — M1 (ядро) + M2 (host), РЕАЛИЗОВАНО 2026-07-21.**
  База остаётся замапленной, мутации идут в отдельный owned-оверлей. Rust
  `Cow` целобуферный (первый `to_mut()` клонирует всю арену), поэтому
  per-page CoW сделан **явным** плоским overlay-слоем (`plugmem-arena::paged`,
  без `Box`/деревьев), не через `Cow`.
  - **M1 (arena + core):** append-only пулы (`BlobHeap`/`VecPool`/`Interner`)
    держат `base:&[u8] + owned tail`; in-place структуры (`Arena`/`ChunkPool`)
    — page-CoW (тронутые страницы копируются, остальные заимствуются).
    `Memory::from_bytes_overlay(snapshot, journal, cfg)` реплеит журнал в
    оверлей без клона базы. Alloc-гейт (`core/tests/zero_alloc.rs`):
    overlay-open аллоцирует **< ¼** owned-open.
  - **M2 (host):** `Database::open` теперь **по умолчанию** mmap'ит снапшот
    и держит движок как overlay; пустая новая база открывается owned и
    переходит в mapped при первом snapshot. `snapshot`/`checkpoint`
    материализуют base+overlay в новый файл и **пере-mmap**-ят его (оверлей
    схлопывается — длинная сессия записи остаётся ограниченной). Порядок
    «материализовать → **размапить** → tmp+fsync+rename → пере-mmap» —
    размап перед rename обязателен (Windows не переименовывает замапленный
    файл). Единственный новый `unsafe` — `Mmap::map`, безопасен эксклюзивным
    локом на весь срок хэндла. `arena` при M2 не тронут.
  - **Что это даёт (измерено `memory-stats`, host-тест):** owned-open держит
    **вторую копию** образа в куче (буфер чтения + копии пулов, пик ~2×);
    overlay-open **не копирует** (пик ~1×, страницы — чистые, вытесняемые,
    разделяемые). На базе 12.6 МБ: owned 24.5 МБ RAM, overlay 12.6 МБ.
    Затык записи «клон 13 ГБ ради одного факта» снят.
  - **Оговорка (M2 сам по себе): no-copy-выигрыш, ещё не sparse.** На дефолтном
    (checksummed) пути загрузчик при открытии читает весь файл ради xxh3, а
    `finish_load`/`validate_references` дополнительно сканировали большие пулы —
    overlay фолтил ~весь образ. Это снято вехой F ниже (для доверенного
    `fast_load`-пути).

- **Веха F — ленивая валидация текста и векторов: РЕАЛИЗОВАНО 2026-07-21**
  (`plugmem-core`, коммит `bf01a1f`). Валидация двух доминирующих пулов
  перенесена с eager-at-open на lazy-at-access (модель SQLite: проверка в
  момент обращения). arena при F1 **не тронут**.
  - **Что снято с открытия:** UTF-8 скан всего текста (`finish_load`) +
    `VecPool::validate` и пер-факт vector-slot bijection (`validate_references`)
    — единственные проверки, читавшие текстовый и векторный пулы.
  - **Акцессоры panic-free:** `get`/`entity_name`/similar/recall-рендер больше
    не `.expect` на `from_utf8` — нечитаемый текст прячет факт / не даёт
    лексического сигнала / рендерит пустое тело, но не паникует; векторный
    поиск и так читает слоты с bounds-check. Контракт «не паниковать на любых
    байтах» теперь покрывает **и load, и любой доступ**.
  - **`Memory::verify()` / `Database::verify()` / `ReadOnlyDatabase::verify()`**
    — on-demand integrity check (аналог SQLite `PRAGMA integrity_check`):
    прогоняет отложенные проверки (UTF-8 свип + vec self-check + bijection),
    превращает скрытую порчу в явный `Corrupt`. Trust-but-verify доступен —
    просто не на каждом open.
  - **Оставлены eager** дешёвые O(метаданных) проверки: заголовок, таблица
    секций (границы срезов mmap), метаданные арен/чанков, HNSW-граф (не читает
    вектор-слоты), ref-диапазоны fact/entity/edge — структурно битый образ
    по-прежнему отвергается при open.
  - **Измерено (host RSS-тест, `fast_load`, text-доминантная база 14 МБ):**
    overlay-open резидентит **4.3 МБ** (< половины файла) — текстовый пул не
    фолтится. Для векторной базы (int8-векторы доминируют, d768×10M ≈ 8.7 ГБ)
    выигрыш кратно больше. **Только `fast_load`**: дефолтный checksummed-путь
    всё равно читает файл ради xxh3 (интегрити на каждом open, цена — не sparse).
  - **Follow-up (веха F2, не сделано):** чанки/постинги (самоограниченный
    `ChunkIter` в arena: bounds-check индекса + budget; снять `validate_chunks`
    link-loop + `validate_chain`), HNSW-граф (bounds-check соседей в поиске),
    fact/entity/edge ref-сканы. Они меньше по объёму и требуют правки
    arena / hnsw-поиска.

- **Векторный RAM — второй рычаг (overlay его НЕ решает).** Overlay
  снимает клон-на-запись и резидентность холодных данных, но не рабочее
  множество векторного поиска: HNSW ходит по пулу случайно, за серию
  запросов ОС подтянет почти все int8-векторы в резидент. Решение — как у
  Qdrant («original on disk, quantized in RAM»): держать в RAM маленький
  тир, полные векторы пейджить. У нас он **уже есть** — 1-битная знаковая
  сигнатура `dim/8` B (d768 → 96 B против 768 B int8), сейчас инлайн в
  слоте `vecpool`. Работа: разнести тиры в отдельные пулы (сигнатуры
  резидентно, int8 в mmap, трогается только на rescore шортлиста). PQ
