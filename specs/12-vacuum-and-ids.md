# 12 — vacuum и logical/physical id (черновик для обсуждения)

> **Статус: ОТКРЫТЫЙ ВОПРОС, не реализовано.** Хендофф для следующей сессии
> (Fable). Здесь зафиксирован дизайн «уплотняющего vacuum с перенумерацией
> id», развилка решений и **один вопрос, который пользователь уточнит**
> прежде чем это реализовывать. Ничего в v1-формате менять не требуется —
> это чистое v2-расширение поверх готового движка.

## 0. Что решаем

`maintain` (этап B, реализован) возвращает **байты содержимого** забытых
фактов, но **сознательно оставляет навсегда** мелкий структурный осадок,
ценой инварианта «id никогда не меняются» (specs/11 B.1):

- **id-скорлупы** — 48-байтная `FactRecord` + 16-байтная `FactAux` каждого
  забытого факта остаются в аренах (id обязан оставаться занятым);
- **мёртвые термы** интернера (слово/тег только от удалённых фактов);
- **осиротевшие сущности** (entity без единого живого факта).

Порядок величин (потолок wasm32 = 2 ГиБ): скорлупа ≈ 64 Б/факт →
память упирается на **~30 млн суммарно забытых фактов**, а id-пространство
(`u32`, ~4.29 млрд) — сильно позже. То есть под патологическим churn узкое
место — накопление скорлуп, не биты id.

**Вопрос пользователя:** можно ли написать алгоритм, который по накоплении
`N` забытых физически всё вычищает и **перенумеровывает** id, не ломая
ссылочную систему и **не роняя производительность**?

**Ответ:** да. Перформанс — не препятствие (алгоритм O(база), как
`maintain`; после него рантайп даже быстрее — данные плотнее). Настоящая
загвоздка — **референциальная целостность наружу движка**, и она решается
разделением логического и физического id. Детали ниже.

## 1. Алгоритм vacuum (детерминированный, O(база))

```
vacuum(store, now):
  # 1. Плотная перенумерация ЖИВЫХ в старом порядке id (tombstone исчезают)
  remap_fact[old]   = new   # только не-tombstone
  remap_entity[old] = new   # заодно можно выкинуть осиротевшие
  remap_term[old]   = new   # только термы с живыми ссылками

  # 2. Пересборка всего с ремапом ВСЕХ внутренних ссылок:
  #    fact.revises  -> remap_fact[..]   ИЛИ NONE, если предок был вычищен
  #    edge.fact     -> remap_fact[..]   ИЛИ NONE
  #    edge a/b, entity_facts ключи      -> remap_entity
  #    postings / temporal ключи         -> новые fact-id
  #    теги / rel / name_term            -> remap_term
  #  Живые в старом порядке -> новые id тоже по возрастанию -> постинги
  #  остаются отсортированы, вставки дешёвые (тот же приём, что в maintain).

  # 3. snapshot + clear_journal   (vacuum = ЧЕКПОИНТ, не replay-маркер)
  # 4. вернуть таблицы remap наружу (для обновления внешних держателей)
```

Это буквально `maintain` + перенумерация. Сложность и стоимость — те же.

**Семантическая тонкость:** если факт ревизил другой, а тот потом забыт и
вычищен, ссылка `revises`/`provenance` указывает в пустоту → ставим `NONE`
(цепочка истории оборвана, но это следствие самого `forget`). Всё прочее
ремапится один-в-один.

**Почему не replay-маркер (в отличие от maintain):** старый журнал ссылается
на старые id; после перенумерации их не воспроизвести. Поэтому vacuum —
это **snapshot-чекпоинт с обнулением журнала**, а не журналируемая
операция. Детерминизм сохраняется вперёд (после vacuum журнал пуст).

## 2. Настоящая загвоздка: ссылки СНАРУЖИ движка

Внутренние ссылки перенумеровать тривиально (см. выше). Ломается ровно
одно: **`FactId`, которые держит вызывающий** (агент сохранил `FactId 42`
в промпте / другой базе / SDK-объекте). Две развилки:

### Развилка A — наружу raw `FactId` НЕ утекает как долговременный хэндл

Тогда перенумерация абсолютно безопасна: движок самосогласован, ремапнули
всё внутри — готово. `vacuum` — простой офлайн-глагол, ноль изменений в
модели. Публичный контракт: «`FactId` — эфемерный, действителен до
следующего vacuum; не сохраняй его надолго».

### Развилка B — наружу `FactId` отдаётся как хэндл (наш вероятный случай)

`remember` возвращает `FactId`, которым потом делают `revise`/`forget`/`get`.
Если SDK/агент **сохраняет** его между сессиями — перенумерация его сломает.
Решение — классический приём БД: **разделить логический и физический id.**

- **физический `FactId` (u32, индекс в арене)** — адресация внутри; vacuum
  свободно перенумеровывает;
- **логический `uid` (u64, монотонный, НИКОГДА не меняется)** — то, что
  отдаём наружу; маленькая таблица `uid → текущий FactId`.

Vacuum перекладывает физические id и обновляет `uid→id`. Внешние `uid`
вечны. **Перф-цена ≈ ноль:** одна hash-выборка на входе в API
(`get/revise/forget` по uid); в горячих циклах recall никаких uid нет.

Это ровно формулировка пользователя: «обнулять id, ненужные менять на
другой, но не ломать ссылочную систему» — не ломается, потому что наружу
торчит стабильный `uid`, а внутри всё перенумеровано и консистентно.

## 3. ГЛАВНЫЙ ВОПРОС К УТОЧНЕНИЮ (пользователь уточнит)

> **Кто и как держит `FactId` вне движка? Наш SDK/обёртки будут его
> сохранять как долговременный хэндл, или он эфемерный?**

От этого зависит развилка:

- **Никто долговременно не хранит** (id живёт в пределах одной сессии/задачи
  агента, всегда получается свежим из recall) → **Развилка A**, `vacuum`
  тривиален, uid не нужен.
- **SDK/агент сохраняет `FactId`** (в своей памяти, в промптах, ссылается
  между сессиями) → **Развилка B**, нужен `uid`-слой в публичном API.

Сейчас (v1) `FactId` де-факто стабильны, поэтому вопрос не всплывал. Как
только вводим vacuum — надо зафиксировать контракт. **Рекомендация:** даже
если сегодня кажется, что развилка A — всё равно заложить `uid` (развилка B)
дешевле сразу, чем потом ломать API; `uid→id` — это ~8-12 Б/факт и одна
секция снапшота. Но это решение пользователя.

## 4. maintain vs vacuum — разграничение (не путать)

| | `maintain` (есть) | `vacuum` (v2, этот док) |
|---|---|---|
| id | **сохраняет** | **перенумеровывает** |
| журнал | replay-маркер (воспроизводим) | **чекпоинт**: snapshot + сброс журнала |
| убирает | байты содержимого забытых | **всё**: скорлупы, мёртвые термы, пустые сущности |
| внешние ссылки | не трогает | нужен `uid`-слой (развилка B), иначе ломает |
| триггер | доля tombstone / политика обёртки | накоплено `N` забытых / реже, «обслуживание» |
| стоимость | O(база) | O(база), тот же порядок |

## 5. Что нужно для реализации (когда решим развилку)

1. **Развилка A:** новый `Memory::vacuum(store, now) -> VacuumReport`; пере-
   нумерующая пересборка (форк `maintain::rebuild` с таблицами remap);
   snapshot+clear_journal; тесты как у maintain (observation-equivalence
   через ремап, каноничность, roundtrip, property) + проверка, что
   `revises`/provenance на вычищенных → NONE.
2. **Развилка B (дополнительно):** поле `uid` в `FactRecord` или отдельная
   `Arena<UidSlot>` (`uid u64 → FactId`), обратная `id→uid` для выдачи
   наружу; публичные глаголы принимают/возвращают `uid`; секция снапшота
   для таблицы; `next_uid` в engine-state. Внутренние индексы и recall не
   меняются (остаются на физическом `FactId`).

Формат v1 при этом не ломается: vacuum — новый глагол, `uid` — новые
секции; старые снапшоты грузятся (uid можно достроить лениво = порядковый).

## 6. Идентичность базы и эпохи vacuum (uuid + epoch) — как «пометить файл»

Пользователь: надо уметь **указать в файле метку**, чтобы люди (и SDK)
понимали — снапшот «до vacuum» или «после», и не нужна ли миграция id.
Механизм — две метки, которые кладём в снапшот:

1. **`db_uuid` (u128, 16 Б) — стабильный id лайнеджа базы.** Минтуется один
   раз при создании базы и **никогда** не меняется (переживает и `maintain`,
   и `vacuum`, и пересохранения). Идентифицирует «это та же самая база».
   Разный `db_uuid` = разные базы, их id несравнимы.
   - Нюанс: ядро `no_std`, у него **нет RNG**. Значит `db_uuid`, как и `now`,
     **приносит хост** при `Memory::new` (параметр/поле Config). Ноль = «база
     без имени» (для эфемерных/тестовых).

2. **`vacuum_epoch` (u64) — поколение нумерации id.** В engine-state,
   стартует с `0`, **+1 при каждом `vacuum`** (`maintain` его НЕ трогает — он
   id не меняет). Это и есть метка «до/после».

**Контракт для внешних держателей id.** Кто сохраняет `FactId` (или `uid`)
надолго — сохраняет тройку `(db_uuid, vacuum_epoch, id)`. При переиспользовании:

| Условие | Смысл |
|---|---|
| `db_uuid` не совпал | другая база — id вообще не про неё |
| `db_uuid` совпал, `epoch` < текущей | **id из «до vacuum» → устарел, нужна миграция** (ремап или сбросить) |
| `epoch` == текущей | id валиден |

То есть сигнал «нужна миграция» — это ровно `stored_epoch < current_epoch`.
(При развилке B с `uid` эпоха не нужна для валидности — `uid` вечен, — но
метка всё равно полезна человеку и для инвалидации кэшей SDK.)

**Для человека / CLI.** `stats()` и `plugmem stats` печатают `db_uuid` +
`vacuum_epoch` (+ `created_at`). Глядя на два файла, видно: та же база или
нет, и какой новее / пост-vacuum. Можно добавить и по-снапшотный
`write_counter` (растёт на каждом сохранении) — для «какой из двух свежее».

**Важно — это НЕ то же, что `version` формата.** Поле `version` в заголовке
(specs/03) ловит смену **байтовой раскладки**. `vacuum_epoch` ортогонален:
это поколение **нумерации id** внутри той же раскладки, и оно важно **только
внешним держателям id** — сам движок грузит свой снапшот всегда
консистентно, эпоху при загрузке не проверяет.

**Куда кладём в формате.** `db_uuid` — в заголовок (там есть резервные
байты) или в config-блок; `vacuum_epoch` — в engine-state (`STATE_LEN`
24 → 32). Обе метки читаются в `stats()`.

**Когда закладывать — можно сейчас, но не обязательно немедленно.** Формат
до первого публичного тега **свободно ломается** (specs/03: «формат
замораживается с первого публичного тега»). Значит форвард-совместимость не
пострадает, если добавить метки **в любой момент до заморозки** — но
**обязательно до первого релиза**, иначе позже это ломающее изменение.
Практичный порядок: сперва решить развилку A/B (§3), затем **одним**
изменением формата заложить `db_uuid` + `vacuum_epoch` (+ таблицу `uid→id`,
если B). Так один раз тронем header/state/config-codec и golden-тесты, а не
трижды.

> **Пункт в чек-лист pre-1.0:** `db_uuid` + `vacuum_epoch` в снапшоте
> **обязаны быть заложены до заморозки формата**, даже если `vacuum` ещё не
> реализован (`epoch` просто стоит `0`). Тогда появление vacuum — не слом
> формата, а инкремент уже существующего поля.

## 7. Резюме для Fable

- Алгоритм перенумерующего vacuum **реализуем и не бьёт по перформансу**
  (O(база), редкий batch; рантайп после — быстрее).
- Единственная преграда — внешние держатели `FactId`; снимается слоем
  `uid` (логический id стабилен, физический перенумеровывается).
- **Не начинать реализацию, пока пользователь не ответит на §3** (кто
  хранит id снаружи → развилка A или B).
- **`db_uuid` + `vacuum_epoch` (§6) — заложить в снапшот ДО заморозки
  формата**, даже без vacuum (epoch = 0). Это метка «до/после vacuum» и
  сигнал «нужна миграция» (`stored_epoch < current_epoch`). Заложить одним
  изменением формата вместе с решением A/B, чтобы не трогать header/state
  дважды. Пункт в чек-лист pre-1.0.
- Приоритет самого vacuum ниже, чем этапы C (testgen) и D (README/стенд) из
  specs/11 — это v2-полировка под churn. **Но метки (§6) — это pre-1.0**,
  их закладка не ждёт vacuum.
